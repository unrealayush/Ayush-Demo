# Common Agent Instructions — AYUSH Bio-AI Evidence Demo

These instructions apply to Gemini CLI, Claude Code, and any coding agent working in this repository.

## Product goal

Build a serious Bio-AI MVP demo for AYUSH anti-infective evidence generation.

The demo must convert:

AYUSH candidate + active marker + pathogen target + antibiotic comparator

into:

docking results + interaction rationale + mechanism graph + validation priority score + Global Evidence Passport.

## Scenario routing (replaces the single core demo case)

Work routes off a `scenario_id` resolved from `configs/scenarios/scenario_registry.yaml` — **never**
off a hardcoded Trikatu/Piperine/NorA case. Selection precedence: `SCENARIO_ID` env var → registry
`default_scenario`. Field schema: `contracts/scenario_schema.md`; selection guide: `docs/16`.

Active scenarios (shipped default = Scenario_1):

- `primary_kuth_pseudomonas` — **default** — Costunolide / Dehydrocostus lactone →
  *Pseudomonas aeruginosa*; targets LasR, PqsR / MvfR; focus: quorum sensing, virulence, biofilm
  maturation.
- `secondary_kuth_staphylococcus` — Costunolide / Dehydrocostus lactone → *Staphylococcus aureus*;
  targets AgrA, Sortase A / SrtA; focus: quorum sensing, adhesion, biofilm initiation.

Archived (reference only, never default):

- `archived_trikatu_prior` — the former single-demo case (Piperine → MRSA/NorA, Ciprofloxacin
  comparator). Preserved at `configs/archived_reference_scenarios/scenario_prior.yaml`.

Scenario rows are **manually curated**: no automatic compound × target cross-products, no
synergy/FICI/checkerboard required fields, and `comparator_control` is nullable for active scenarios.
Study/Infection Context and the no-patient-data rule below apply to every scenario.

## Keep MVP simple

Visible model stack:

1. Ligand preparation: RDKit / Open Babel
2. Target structure resolver: PDB first, AlphaFold DB second, ESMFold2 fallback only
3. AI docking: DiffDock-L
4. Classical docking baseline: AutoDock Vina
5. Interaction parser: contact and residue analysis
6. Evidence passport: Gemini on Vertex AI or local mock mode if API unavailable

Do not add GNINA, ESM-2, ChemBERTa, GNN, GraphSAGE, patient omics, or host patient models in the first MVP.

## Patient data rule

Do not use real patient data in the first demo.

Do not label the fourth input as "Host Patient Context".

Use:

- Study Context
- Infection Context
- Preclinical Discovery Mode

Acceptable chips:

- biofilm-high
- efflux-associated
- wound isolate context
- preclinical validation

## No hallucination rules

- Never invent PDB IDs, UniProt IDs, PubChem CIDs, ChEMBL IDs, SMILES, docking scores, residues, or assay values.
- If a real dataset cannot be fetched, mark it as `missing_real_data`.
- If a synthetic fallback is used, mark every row as `evidence_level=synthetic_demo` (identity columns may never be synthetic).
- If a docking run fails, show `run_status=failed` and do not fabricate scores.
- If no good target structure exists, show `structure_pending` and skip docking for that target.
- Any numerical score shown in UI must be traceable to a JSON output file generated by a model module or explicitly marked as demo placeholder.
- These rules are machine-enforced by `validate_contracts` (`docs/10`). The allowed/forbidden scientific-language wordlist is the single copy in `contracts/scientific_language.yaml`; controlled values (evidence_level, enums, provenance) live in `contracts/vocabularies.md`.

## Output interpretation

- DiffDock-L confidence = pose confidence, not binding affinity.
- Vina score = classical docking score, not experimental binding affinity.
- AI Combination Plausibility = prioritization for validation, not wet-lab synergy.
- Validation Priority Score = wet-lab prioritization score, not efficacy.
- Evidence Passport = research-use-only evidence dossier, not clinical guidance.

## Agent team and run modes

- The build is executed by 10 agents (`docs/06`): managed-mvp-coordinator, dataset-curator,
  ligand-prep-engineer, target-structure-resolver, docking-pipeline-architect, interaction-analyst,
  evidence-passport-designer, qa-contracts-validator, scientific-validity-reviewer,
  gcp-deployment-architect.
- Run modes (`docs/04`): `local-planning | mock | real-data-fetch | real-docking | gcp-deployment | demo`.
  The ministry demo runs `RUN_MODE=demo` over REAL artifacts; `run_status=mock` is forbidden in the demo.
- `validate_contracts` (`docs/10`) runs at Gate 0 and every agent handoff.
- Phase 0 only — Phase 1–6 items (WGS, RNA-Seq, LC/GC-MS, MIC/FICI/biofilm, GNINA/ESM-2/ChemBERTa/GNN,
  in-vivo, patient omics) are Future Roadmap (`docs/11`), not MVP build scope.

## Acceptance criteria

Before demo, the agent must produce (paths per `contracts/vocabularies.md` §8) for the active
`scenario_id` (default `primary_kuth_pseudomonas`):

- `outputs/run_manifest.json` (carries the resolved `scenario_id`)
- `outputs/source_traceability.csv`
- `outputs/input_validation_report.json`
- `outputs/ligand_prep_report.json`
- `outputs/target_selection.json`
- `outputs/structure_resolution_report.json`
- `outputs/diffdock/diffdock_results.json`
- `outputs/vina/vina_results.json`
- `outputs/interaction_summary.json`
- `outputs/mechanism_graph.json`
- `outputs/combination_plausibility.json`
- `outputs/evidence_passport.json` (+ `evidence_passport.md`)
- `outputs/validation_report.json` (validate_contracts green)
- UI rendering that reads only from output files, not hardcoded scores
